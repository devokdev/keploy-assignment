Traditional backend integration testing requires writing extensive boilerplate: spin up temporary test databases, handcraft mock handlers, curate brittle JSON fixtures, and continually update test assertions whenever endpoint schemas change.

**Keploy approaches testing from the opposite direction.** Instead of hand-authoring mock fixtures, Keploy sits on the network boundary of your application process or container, records real inbound HTTP requests and outbound I/O calls (such as Redis queries), and automatically generates deterministic test specifications (`test-1.yml`) and mock files (`mocks.yml`).

In this tutorial, you will walk through the entire lifecycle:
1. Start a real Go Gin authentication service with a Redis dependency.
2. Put Keploy into **record mode** to observe API traffic.
3. Send real HTTP requests to generate an OTP verification flow.
4. Inspect the generated test cases and understand why dynamic fields (OTP, dates) are categorized as noise.
5. Replay the captured behavior with `keploy test`—running tests without depending on a live Redis instance.

## What We Are Building

The tutorial uses a realistic Go authentication sample built with the **Gin** web framework and **Redis**.

The service provides two core endpoints:
- `GET /api/getVerificationCode?email=...&username=...`: Generates a random 4-digit OTP and stores it in Redis with an expiration TTL.
- `POST /api/verifyCode`: Validates the submitted OTP against Redis.

## Prerequisites

Before starting, ensure you have the following installed on your development machine:

1. **[Docker & Docker Compose](https://docs.docker.com/get-docker/)**: Used to run Redis and containerized application builds.
2. **[Go 1.20+](https://go.dev/doc/install)**: Required if compiling Go binaries locally (`go version`).
3. **[Keploy CLI v2+](https://github.com/keploy/keploy)**: The test generation engine.
4. **[Git & cURL](https://git-scm.com/)**: To clone sample code and exercise API endpoints.

To install the Keploy CLI on Linux, macOS, or WSL2:

```bash
curl --silent --location https://github.com/keploy/keploy/releases/latest/download/keploy_linux_amd64.tar.gz | tar xz -C /tmp
sudo mv /tmp/keploy /usr/local/bin/keploy
```

Verify your Keploy installation:

```bash
keploy --version
```

<section id="step-2-start-redis">

## <span className="step-pill">Step 02</span> Start Redis

<FlowDiagram compact activeStep="redis" stepNumber="STEP 02 / 07" stepTitle="Start Redis Cache" />

Start the Redis dependency in detached mode using Docker Compose:

```bash
docker compose up -d redis
```

<Callout type="why" title="Why must Redis be running during record mode?">
During recording, the Go application communicates with a <strong>real</strong> Redis instance. Keploy listens to the TCP socket traffic between Gin and Redis, intercepting commands like <code>SET email:otp 2121 EX 300</code> and caching the real response into <code>mocks.yml</code>. Once recorded, you will no longer need Redis running to execute your tests.
</Callout>

Verify that Redis is healthy and accepting connections:

```bash
docker ps --filter "name=redis"
```

<section id="step-4-start-recording">

## <span className="step-pill">Step 04</span> Start Recording with Keploy

<FlowDiagram compact activeStep="record" stepNumber="STEP 04 / 07" stepTitle="Activate Keploy Record Mode" />

Launch the application container wrapped inside Keploy's `record` command:

```bash
keploy record -c "docker run -p 3001:3001 --network gin-redis_default --name ginRedisApp gin-app:1.0"
```

### What is happening behind the scenes?

When you execute `keploy record`:
1. Keploy creates an interception layer at the network and process boundary.
2. It executes your containerized application (`gin-app:1.0`) connected to the shared Docker network.
3. Keploy monitors port `3001` for inbound HTTP traffic and tracks outgoing TCP sockets connected to Redis (port `6379`).
4. The terminal will log that Keploy is listening and ready to record user interactions.

<Callout type="info" title="Zero Source Code Intrusion">
Notice that we did not import SDKs, decorate Go structs, or modify any handlers in <code>main.go</code>. Keploy operates transparently at the I/O layer.
</Callout>

</section>

<section id="step-5-exercise-api">

## <span className="step-pill">Step 05</span> Exercise the API to Capture Behavior

<FlowDiagram compact activeStep="request" stepNumber="STEP 05 / 07" stepTitle="Trigger Real API Traffic" />

Open a second terminal window. We will make HTTP requests against the running service. These real requests are the exact events Keploy will observe and convert into regression test cases.

### 1. Request an OTP Verification Code

```bash
curl --location 'localhost:3001/api/getVerificationCode?email=dev@example.com&username=shivam'
```

**Expected Response:**

```json
{
  "data": {
    "otp": 2121
  },
  "msg": "OTP sent successfully"
}
```

### 2. Verify the OTP Code

Send the verification request with the generated OTP and email payload:

```bash
curl --location 'localhost:3001/api/verifyCode' \
  --header 'Content-Type: application/json' \
  --data-raw '{
    "otp": 2121,
    "email": "dev@example.com"
  }'
```

**Expected Response:**

```json
{
  "data": null,
  "msg": "OTP verified successfully"
}
```

Switch back to the terminal running `keploy record`. You will see Keploy log that it captured the incoming HTTP transactions and their corresponding Redis read/write calls:

```text
🐰 Keploy captured test case: test-1 (POST /api/getVerificationCode)
🐰 Keploy captured test case: test-2 (POST /api/verifyCode)
📁 Stored test cases in: ./keploy/test-set-0/tests/
📁 Stored dependency mocks in: ./keploy/test-set-0/mocks.yml
```

Stop the recording session by pressing `Ctrl + C`. Keploy will gracefully shut down the container and flush artifacts to disk.

## <span className="step-pill">Step 06</span> Inspect What Keploy Generated

<FlowDiagram compact activeStep="artifacts" stepNumber="STEP 06 / 07" stepTitle="Understand Test & Mock Artifacts" />

Keploy stores all captured test specifications in human-readable, declarative YAML files under the `keploy/` directory:
- `test-1.yml`: The HTTP test case recording request parameters, status code, response body, and assertions.
- `mocks.yml`: The captured Redis interactions (commands like `SET`, `GET`, connection handshakes).

### Annotated Test Spec (`test-1.yml`)

<AnnotatedYaml title="keploy/test-set-0/tests/test-1.yml" />

### Understanding the `assertions.noise` Section

A critical challenge with automated testing of real applications is **non-deterministic data**. 

In our authentication endpoint:
- The **OTP** (`2121`) changes randomly on every single invocation.
- The HTTP **Date** header updates continuously.

If a test framework performed a strict byte-for-byte diff against the original response, every subsequent test run would fail falsely. 

Keploy detects or allows configuring dynamic paths under `assertions.noise`. When replaying tests, Keploy verifies that the schema structure and static fields match, while ignoring the unpredictable noise values.

### Inspecting Redis Mocks (`mocks.yml`)

```yaml
version: api.keploy.io/v1beta1
kind: Generic
name: mock-0
spec:
  metadata:
    type: redis
    operation: SET
  req:
    data: "SET dev@example.com:otp 2121 EX 300"
  resp:
    data: "OK"
```

<Callout type="why" title="What does mocks.yml do during tests?">
When replaying tests, the application will attempt to talk to Redis. Instead of routing traffic to a live Redis server, Keploy intercepts the outgoing TCP call and returns the recorded <code>"OK"</code> response directly. This eliminates the need for test databases in CI pipelines.
</Callout>

## <span className="step-pill">Step 07</span> Replay the Behavior with `keploy test`

<FlowDiagram compact activeStep="replay" stepNumber="STEP 07 / 07" stepTitle="Execute Replay Test Suite" />

Now verify that the captured behavior can be replayed deterministically without manual test scripts.

Execute the test command:

```bash
keploy test -c "docker run -p 3001:3001 --rm --network gin-redis_default --name ginRedisApp gin-app:1.0" --delay 10
```

<Callout type="info" title="Why the --delay 10 flag?">
The <code>--delay 10</code> flag gives the Docker container up to 10 seconds to finish booting the Go binary, establishing internal network routes, and binding port 3001 before Keploy sends the replayed requests.
</Callout>

### What Keploy does during test replay:

1. Starts the application container in a sandboxed test harness.
2. Intercepts the application's outbound Redis connections and binds them to `mocks.yml`.
3. Injects the recorded HTTP requests (`/api/getVerificationCode`, `/api/verifyCode`) in sequence.
4. Compares live responses against `test-1.yml` and `test-2.yml`, filtering out defined noise fields.

### Test Execution Output:

```text

  [PASS] test-1 (GET /api/getVerificationCode) - Status: 200 (Duration: 18ms)
  [PASS] test-2 (POST /api/verifyCode) - Status: 200 (Duration: 14ms)

--------------------------------------------------------------------

  Total tests: 2
  Passed: 2
```

<section id="troubleshooting">

## Troubleshooting & Common Mistakes

<GotchaAccordion title="Mistake 1: Redis is not running or unreachable on Docker network" defaultOpen={true}>
<p>If the application crashes on startup with connection refused errors, make sure you ran <code>docker compose up -d redis</code> and that both containers are attached to the same Docker network (e.g. <code>gin-redis_default</code>).</p>
</GotchaAccordion>

<GotchaAccordion title="Mistake 2: Test times out before app is ready (--delay flag)">
<p>If Keploy sends requests before Gin binds port 3001, you may see connection errors. Increase the delay parameter (e.g. <code>--delay 10</code> or <code>--delay 15</code>) to give containerized apps adequate bootstrap time.</p>
</GotchaAccordion>

<GotchaAccordion title="Mistake 3: Port 3001 conflict with existing local processes">
<p>If another application is already listening on port 3001, Docker will fail to bind the port. Stop competing services or adjust port mapping in the command.</p>
</GotchaAccordion>

<GotchaAccordion title="Mistake 4: Running Keploy commands from the wrong working directory">
<p>Keploy reads and writes artifacts relative to the current directory (<code>./keploy/</code>). Ensure you execute all commands from the root of the <code>gin-redis</code> project directory.</p>
</GotchaAccordion>

## Conclusion

Writing comprehensive regression test suites for distributed services does not require spending hours handcrafting synthetic database fixtures and brittle mocks.

By recording real interactions once and replaying them deterministically as version-controlled YAML tests, Keploy allows Go developers to achieve deep regression test coverage with zero production code changes.
